# KiteSink

The personal site for **kitesink.com** — one person's workshop, organised into five sections:
**Consulting · Fitness · Music · Library · About**.

Plain static HTML/CSS/JS. No build step, no framework, no runtime dependency. Every page
runs in any browser by opening the file directly.

## How the site is organised (2027 refresh)

| Section | Hub page | What lives under it |
|---|---|---|
| Consulting | `/consulting` | Services for music teams, how a project runs, the AI concierge offer, an enquiry form |
| Fitness | `/fitness` | Vantix (`/vantix`, privacy), thirteen free calculators (among them a diet planner, heart-rate zones, FFMI and a supplement checker, sharing one My numbers panel), and a field guide: `/fitness` is its hub (search and a card per page) and sixteen pages sit under `/fitness/`, twelve areas plus claims, glossary, reference and sources |
| Music | `/music` | Song of the Day, Stage First (the product that absorbs Backline; `/backline` redirects to it), Album Listening Club |
| Library | `/library` | **Everything** — every project, tool, game, post and page, searchable. `/games`, `/blog` and Campground Tycoon live here. The old `/work` index is gone and redirects here |
| About | `/about` | About, Now, Uses |

The home page (`/`) is the landing page: a five-row index of the sections, a card deck that
responds to it, then one band per section.

**Nothing was deleted in the refresh.** Every pre-existing page still exists at the same URL;
the product pages (Vantix, Stage First, Song of the Day, Campground Tycoon, Listening Club) keep
their own art direction and only their KiteSink nav changed.

## Changing things

- **Add a page:** create the HTML, then add one entry to `public/site-index.js` and one line to
  `public/sitemap.xml`. `scripts/check_site.py` fails if you forget either, so a page can't
  become unreachable.
- **Change the nav / sections:** `SECTIONS` at the top of `public/ks.js`. The blog
  post template carries its own small KiteSink nav — search for `/consulting` in that file.
  Every other page mounts the shared header or slim bar.
- **Change `ks.css`, `ks.js`, `site-index.js`, `fitness.js`, `fitness.css` or `fitness-ref.js`:** bump the `?v=2027.23` (the current number) on the
  `<link>`/`<script>` tags in every page (find-and-replace) and `ASSET_V` at the top of `ks.js`. Those files are cached for an hour or more, and a new page with an
  old cached stylesheet looks broken. The audit checks every page uses the same version.
  The fitness pages are generated, so change the number in `content/fitness/page.html` and
  `content/fitness/templates/sub.html`, then run the build.
- **Design tokens:** `--k-*` custom properties at the top of `ks.css` (light + dark). New pages
  opt into the component kit with `<body class="ks-paper k2">`.
- **Fitness entries:** `/fitness` (the hub) and the sixteen pages under `/fitness/` are generated. Add or
  change an entry in the right file in `content/fitness/` (the format is in
  `content/fitness/WRITING-BRIEF.md`), then run
  `python3 scripts/validate_fitness.py content/fitness/<file>.json` (it checks every source
  against Crossref), `python3 scripts/build_fitness.py` and `python3 scripts/build_llms_full.py`.
  The hero, the search box, the Vantix card and the calculators live in `content/fitness/page.html`.
  The hero's goals live in `content/fitness/hero.json`: for each goal, the share of max the bar
  loads (and the entry that gives it, or none when it is an example), a typical week, the entry
  its card shows, and the tools and areas it rings, with overrides per level of experience. The
  build checks every id, area and tool in it, so a renamed entry fails the build, not the page.
  - **The calculators' numbers** come from the guide, never typed into `fitness.js`.
    `content/fitness/tool-data.json` names the entry behind each (the zone scale, the IPF classes,
    the FFMI landmarks, the RPE chart, the supplement rows…); the build parses it and stops if an
    entry goes or a table's columns or rows change shape. Each guide table and entry ships once:
    the page prints it (the no-script view and the visible source) and `#tool-data` carries only
    the numbers, which the scripts join to the printed words (`TOOL_SHIP` in the build script). In `page.html`,
    `{{e:<id>}}` links an entry, `{{tools:entry:<id>}}` shows it as a card, `{{tools:table:<id>}}`
    prints a guide table, and the count of calculators is filled from the tabs. A new tool needs
    a tab, a label in `hero.json`'s `tools`, a row in `public/site-index.js` and a line in the
    twin's list (`md_index` in the build script).
  - **My numbers** (`localStorage.ksFit.me`) holds the numbers every tool shares. A field is the
    visitor's only once they type it; tools show examples otherwise, say so, and never save them.
    `KSFit.migrate` builds it once from the keys the tools saved before; the tools still write
    those keys too, for a cached older `fitness.js`. `node scripts/test_fitness.js` covers both.
  The audit fails if a page is older than its data. Every entry names its source and how well
  supported it is; keep it that way.
  - **The hub** lists every page under it as a card, grouped as `GROUPS` in the build script
    says, and still shows them with scripts off. Its search box reads `public/fitness/search.json`,
    which the build writes and the page fetches only when the box is first used. The counts on
    the hub come from the build; do not type them into `page.html`.
  - **Every entry has one home page.** A term lives on `/fitness/glossary`, a claim on
    `/fitness/claims`, everything else on its area's page. The build puts it there and makes
    every other page link to it; nothing is written twice. Once an entry is published, do not
    change its `id`: links to it use that id.
  - **Old links keep working.** The one-page `/fitness` put everything at `/fitness#<id>`. The
    first script in the hub's `<head>` looks such an id up in `public/fitness/ids.json` (every
    entry, every source, and every section id the old page had) and goes to the page that holds
    it, keeping the fragment. An id that is an element of the hub (`#tools`, `#macros`) is never
    looked up. `LEGACY_SECTIONS` in the build script says where each old section went.
    `scripts/fixtures/fitness-legacy-ids.txt` is the list of old ids: the build and the audit
    fail if one of them is neither on the hub nor sent to a page that has it. Do not edit that file.
  - **Sources:** papers with Schoenfeld among the authors may be used, sparingly; the validator
    allows at most five in a file. When sources disagree, prefer the newest good evidence, and
    where this guide and bodyrecomposition.com disagree, defer to that site's position over the
    wording already here unless newer primary evidence says otherwise. Always in your own words,
    with the author named and linked. A credited web article is a source of type `article`.
    The full rules are in `content/fitness/WRITING-BRIEF.md`.
  - **A source's id on the page is its key** (`src-<key>`). If two different sources share a key,
    the second gets a suffix made from its own address. `source_keys` in
    `content/fitness/meta.json` pins a published id so it never moves. The first file that has a
    source settles its key, in the order of `SOURCE_ORDER` in the build script, which is why a
    new file goes at the end of that list.
  - **If a published entry changes what it says,** add a dated row to
    `content/fitness/corrections.json`. It shows on `/fitness/sources`.
  - **A page's title, description, heading and lead** are in `content/fitness/routes.json`;
    the shell around every one of those pages is `content/fitness/templates/sub.html`.
  - **To add an area:** write `content/fitness/<area>.json` and validate it. In
    `scripts/build_fitness.py` add it to `DOMAINS` (label and one-line blurb, at its place in
    the order), to a group in `GROUPS`, and to the end of `SOURCE_ORDER`. Give it a row in
    `routes.json`. Run the build: the hub card, the navigation, the page, its twin, the search
    index and the id map follow. Then list the page, by hand: one line each in
    `public/site-index.js`, `public/sitemap.xml` and `public/llms.txt`, and its route in
    `run_worker_first` in `wrangler.jsonc`. Run `python3 scripts/build_llms_full.py`.
    The audit says which of these is missing.
- **Plain-text twins:** when a fact changes on a page that has a twin (`public/<page>.md`),
  change the twin too. See `docs/AI-PAGES.md`.

## Local preview

These are static files — just open `public/index.html` in a browser, or serve the folder:

```bash
cd public && python3 -m http.server 8000   # then visit http://localhost:8000
```

(Use a server rather than `file://` so root-relative links like `/about` resolve.)

Extensionless URLs (`/fitness`, `/about`) are how the site links to itself, and Python's
server doesn't resolve them. Wrangler's local server does, and behaves like production:

```bash
npx wrangler dev        # serves ./public on http://localhost:8787 — local only, deploys nothing
```

Run both checks before committing:

```bash
python3 scripts/check_site.py
```

```bash
node scripts/test_fitness.js
```

## How this was built

The pages were hand-converted from design-tool exports (`source/`) that relied on a
proprietary runtime (`support.js`). The conversion inlined all styles, expanded the
templating/loops, and reimplemented the interactive bits (clock, blog filter, reading
progress, FAQ accordion, theme switcher, Campground demo controls) in small vanilla JS —
so nothing depends on an external runtime anymore.
